How Mission Control works

A local, no-install command center for every Claude Code project you run. A Python scanner reads your project folders, Claude sessions, and git; a static dark dashboard renders the picture. No server, no build step, no database.

Python stdlib + git Static HTML (file://) No install Travels with your repos

What it is

Mission Control answers one question every morning: across all my projects, where do things stand and what's next? It pulls together status, milestones, todos, recent activity, Claude usage & spend, architecture diagrams, and a per-project knowledge base — into a single dashboard you open as a local file.

It is project-centric: the spine is your ~/Startups/* folders. Everything else is joined onto those real folders. There is nothing to log into and nothing running in the background — you (or Claude) run one script when you want fresh data.

Two moving parts

generate.py scans the filesystem and writes data.js. index.html + project.html read that file and render. That's the whole system.

Source of truth = your repo

Status notes, journals, and diagrams live inside each project folder, so they commit with the code and travel with it. The dashboard is just a view.

The scanner (generate.py)

Pure Python standard library plus the local git binary — no pip install, ever. For each project folder it gathers: the status note, Claude Code session stats & usage cost, git status & recent commits, the knowledge base, the architecture diagram, and the file tree. It also reads global skills/agents from ~/.claude and the connected MCP servers from claude mcp list. Everything is written into a single data.js.

The dashboards (static HTML)

index.html is the portfolio overview: KPIs, a usage & spend layer (estimated Claude cost + Higgsfield credits with renewal dates), an activity chart, and a card per project. project.html?id=<folder> is the drilldown: status, milestones, todos, knowledge base, an interactive architecture diagram, Claude usage, and the file tree. They load Chart.js, Cytoscape.js and marked.js from a CDN but otherwise run as plain files.

Why a snapshot file? Embedding the data inline in data.js means the HTML works straight off file:// with no server and no cross-origin fetch. The trade-off: the numbers are current as of the last generate.py run, which is why the refresh habit below matters.

How it tracks projects

The spine is your ~/Startups/* folders. Onto each one the scanner joins these signals — all optional, all degrading gracefully (a missing input just drops its panel):

SignalSourceWhat it gives
Status note<project>/mission-control.mdstatus, next action, milestones, todos, summary, tech chips
Claude sessions~/.claude/projects/<encoded>/session count, last active, memory files, token usage & est. cost
Gitthe project's .gitbranch, dirty count, ahead/behind, last commit, 30-day commit activity
Knowledge base<project>/knowledge/session journal, architecture spec, free-form notes
Architecture<project>/tech-architecture.jsoninteractive system diagram (tiers, nodes, flows)
Usage & spendsession logs + Higgsfield JSONportfolio Claude cost (est.) and Higgsfield credit balance/burn

The "encoded" Claude path = the project's absolute path with every non-alphanumeric character turned into -, e.g. /Users/you/Startups/my-app → -Users-you-Startups-my-app. That is how a folder is matched to its Claude session history.

One startup per session. Each working session focuses on a single project, and the end-of-session commands only ever edit that project's files. Your portfolio stays cleanly separated.

The status note — mission-control.md

YAML-style frontmatter plus a one-paragraph summary. Every field is optional:

---
name: My Project
status: active            # active | in-progress | blocked | idle | archived
stack: Next.js / Postgres
tech: Next.js, Postgres, Stripe   # comma list → tech-stack chips
next: Ship the checkout flow
tags: saas, p0
milestones:
  - [x] Auth
  - [ ] Billing
todos:
  - Wire the webhook
---
One paragraph on where things stand.

The diagram — tech-architecture.json

tiers are grouped boxes (top→bottom), nodes have a kind (drives colour), edges have a flow (drives colour; add "dashed": true for async):

{
  "title": "My Project",
  "tiers": [{ "id":"client", "label":"01 · Client" }],
  "nodes": [{ "id":"app", "label":"Web App", "tier":"client", "kind":"client" }],
  "edges": [{ "source":"app", "target":"api", "flow":"read" }]
}

kind: client · edge · service · core · store · external  ·  flow: read · control · data · write · feedback · async

Your knowledge base

Every project can carry a knowledge/ folder — plain markdown that commits with the code. It's separate from the mission-control.md status note: the note is a snapshot (status, next, todos, overwritten each update), while the knowledge base is durable history and reference that accumulates over time. It's also what lets a session start informed instead of from scratch.

What's in it

FileRoleWho writes it
journal.mdAppend-only session log (newest on top) — what happened, decisions, blockers. The durable history the snapshot note discards./update
context.mdGenerated digest: status, next, open todos + the last 2–3 journal entries. Auto-loaded into every session via the CLAUDE.md import.generated — don't edit
architecture.mdOptional deep tech spec (module map, schema, flows). Featured in full on the project page.you / /update-arch
*.mdFree-form notes — decisions, references, research. Shown as notes in the Knowledge panel.you

How it's used

Smarter, cheaper sessions

Each project's CLAUDE.md auto-loads context.md (@knowledge/context.md). A session starts already knowing status, next action, and recent history — no re-explaining, and the small stable digest stays cache-warm.

Journal-aware /update

/update reads the recent journal for context, then appends a new dated entry. History compounds instead of being overwritten.

And on the dashboard, project.html renders a Knowledge base panel — the recent journal, the featured architecture spec, and your notes — plus excerpts of the project's Claude Code memory files.

The three-legged memory. Status lives in mission-control.md (the snapshot), history & reference in knowledge/ (journal + spec + notes), and the system's shape in tech-architecture.json (the diagram). Together they let any session — or any teammate — pick up a project cold.

Browse & edit it in Obsidian

Optional. The knowledge base is just markdown, so Obsidian gives you a nice editor with backlinks, tags, search, and a graph view. The dashboard stays the canonical viewer and /update still writes the files — Obsidian is just a comfortable way to read and hand-edit notes.

1

Install Obsidian

Free from obsidian.md. No account required.

2

Open a folder as a vault

Choose Open folder as vault → pick ~/Startups to browse your whole portfolio as one vault. For a tighter scope, open a single project folder, or just its knowledge/ folder.

3

Let it create its config

Obsidian writes a .obsidian/ folder in the vault root (its settings). If the vault is a git repo, you'll likely want .obsidian/ in .gitignore.

4

Browse

Every .md becomes a note: journal.md, architecture.md, and your notes render with full formatting. [[wikilinks]] and #tags work, and the Graph view shows how notes connect.

5

Edit your own notes

Add decisions, references, or research as new .md files in a project's knowledge/ folder, or hand-tweak the journal. They're just files — they show up on the dashboard on the next refresh.

Two things not to touch in Obsidian: context.md is generated — any edits get overwritten next time generate.py / /update runs (edit mission-control.md or journal.md instead). And data.js isn't a note, it's the generated snapshot. After editing notes in Obsidian, run python3 generate.py (or /update) so the dashboard picks up the change.

The daily workflow

The loop is deliberately simple: work, then run one command at the end. Each end-of-session command updates the right files and re-runs generate.py for you, so the dashboard is always current after you use one.

1

Open a session in a project

The session starts informed: each project's CLAUDE.md auto-loads its generated digest (@knowledge/context.md) — current status, next action, and the last few journal entries. No re-explaining.

2

Do the work

Build, fix, ship — normally. Mission Control stays out of the way.

3

Run /update at the end

Refreshes that project's mission-control.md (status, next, milestones, todos, summary) and appends a dated entry to knowledge/journal.md. That journal entry is the durable history the snapshot note discards — and it feeds tomorrow's digest.

4

When the architecture changed → /update-arch

Updates the three tech-knowledge tiers: the tech-architecture.json diagram, the Architecture brief in CLAUDE.md (always-on), and the knowledge/architecture.md deep spec (on-demand).

5

When you used Higgsfield → /update-usage

Pulls fresh credit balance + transaction history via the Higgsfield MCP and rewrites the two JSON files. (Claude usage needs no command — it's read from session logs automatically.)

The shared loop. Every command ends by running generate.py, which rebuilds data.js and each project's knowledge/context.md digest. So updating today's status automatically makes the next session start informed — and keeps re-reading that context cheap (the digest is small and stable, so it stays in the prompt cache).

Set it up in your environment

Mission Control assumes all your projects live under one parent folder. You clone it into that folder, alongside your projects, and run one script. The scanner auto-detects the projects root as the folder that contains the checkout — so there's nothing to hand-edit.

Quick start — three commands

# 1. go to the folder that holds all your projects
cd ~/Startups
# 2. clone the dashboard in beside them
git clone <repo-url> mission-control
# 3. run setup, then open the dashboard
cd mission-control && ./setup.sh
open index.html

No ~/Startups? Clone wherever your projects live — the root is auto-detected. Or override it: MC_ROOT=/path/to/projects ./setup.sh.

What setup.sh does

  • Checks for python3 (and git, optional).
  • Installs the /update, /update-arch, /update-usage, /update-news commands into ~/.claude/commands/ — rewriting paths if your root isn't ~/Startups.
  • Runs generate.py to build data.js and each project's digest.
  • Prints the next steps. It's idempotent — re-run it after a git pull to refresh the commands.

Resulting structure

~/Startups/                  # the parent — one folder per project
├─ mission-control/        # this repo (cloned in beside your projects)
├─ my-first-project/       # your real projects, side by side
│   ├─ mission-control.md
│   └─ knowledge/journal.md
└─ my-second-project/

Then, per project (all optional)

1

Add a status note

Create <project>/mission-control.md using the frontmatter template above. Even just status + next is enough; projects with no note still show derived data (sessions, git, last active).

2

(Optional) add a knowledge folder & diagram

<project>/knowledge/journal.md for history, <project>/tech-architecture.json for the diagram. Each adds its own dashboard panel when present.

3

Wire the auto-loaded digest

After the first setup.sh (which creates each knowledge/context.md), add one line near the top of the project's CLAUDE.md:

@knowledge/context.md

The first import shows a one-time approval dialog; after that, every session in that project starts with the current digest.

4

Run /update as you work

At the end of a session, /update refreshes that project's note + journal and regenerates the dashboard. That's the daily habit.

Excluding folders & optional Higgsfield. To skip scratch/shared folders, add their names to the EXCLUDE set near the top of generate.py. The Higgsfield credit cards only appear if you add higgsfield-usage.json / higgsfield-transactions.json (via /update-usage); skip them and everything else still works.
Open-sourcing your fork? The included .gitignore keeps your personal data out of git — data.js, the Higgsfield JSON, and generated context.md files. Your projects' own notes live in their own folders, so cloning/pushing mission-control/ never carries them along.

Commands cheat-sheet

After the one-time setup, keeping Mission Control current is light. The only thing you truly do daily is run /update at the end of a session — it refreshes everything else for you.

daily
/update

End of every working session. Updates the status note + appends a journal entry, then regenerates the dashboard & digest. This is the habit that keeps the whole system alive.

when it changes
/update-arch

Only when the system's architecture changed. Refreshes the diagram + the CLAUDE.md brief + the deep spec.

when it changes
/update-usage

When you've used Higgsfield and want fresh credit numbers. Needs the Higgsfield MCP connected.

any time
python3 generate.py

Manual refresh. Picks up derived changes (new commits, sessions, usage) without touching your notes. Runs automatically inside every /update* command and when you open a Mission Control session.

one-time
/init

Per project, when bootstrapping its CLAUDE.md architecture brief from the codebase.

The minimum that keeps it current: run /update when you finish working on a project. That single command updates the note, logs the journal, refreshes the digest, and rebuilds the dashboard. Everything else is occasional.
